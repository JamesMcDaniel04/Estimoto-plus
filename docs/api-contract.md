# Estimoto + API v1

This describes the current source contract, including changes prepared for build 8. It does not assert deployment or mobile distribution; see [release status](release-status.md) and the revision-specific release records. Current Alembic head: `a4c1e7b9d2f0`.

All customer routes require `Authorization: Bearer <Supabase access token>`. JSON uses snake_case. Unknown fields are rejected on writes. Errors use `{"detail":"customer-safe explanation"}`. A definitive provider rejection before request creation adds `"code":"request_not_created"` with HTTP409; clients may clear that rejected operation. That rejection is a durable terminal outcome for the customer/key/body, including after provider eligibility changes. The same applies to request rejection for an unavailable owned vehicle or invalid saved ZIP. Creation and rejection decisions serialize through a customer-row database lock; delayed same-key calls cannot convert a rejected operation into a request or classify an existing request as not created. Changing the body for a previously used key conflicts. An unclassified409/idempotency conflict or transport failure must retain its pending retry identity. All IDs are opaque strings and every private lookup enforces authenticated ownership.

`GET /v1/bootstrap` returns an object with `profile`, `vehicles`, `providers`, `estimates`, `repairs`, `requests`, `reminders`, and `capabilities`. Each collection is an array. Capabilities includes `live_requests`, `live_estimates`, `live_discovery`, `carfax`, `youtube_search`, `demo` booleans plus `required_estimate_photo_keys` and `pdr_damage_panel_types` arrays. The client must not infer live capabilities from the presence of sample rows.

Profile: `id`, `email`, `name`, `phone`, `postal_code`, `contact_preference` (`email` or `phone`) and `email_updates` (boolean, changed through the notifications preference route). `PUT /v1/profile` accepts name, phone, postal_code, contact_preference. Bootstrap also carries `unread_notifications`, the count of unread activity notices.

Vehicle: `id`, `nickname`, `year`, `make`, `model`, `vin`, `mileage`, `insurer`, `policy_number`, and nullable `image_version`. `POST /v1/vehicles`, `PUT /v1/vehicles/{id}`, `DELETE /v1/vehicles/{id}`. Required fields: year, make, model; defaults: empty strings, mileage 0. Deletion of referenced vehicles returns 409.

Provider: `id`, `source_id`, `name`, `kind` (`shop` or `technician`), `specialties` (array of `pdr`, `collision`, `maintenance`, `mechanical`), `postal_codes` (array of exact supported postal codes), `city`, `address`, `phone`, `mobile_service`, `accepting_requests`, `description`, and nullable `media`. `media` is either `null` or `{url,kind:"logo"|"photo",attribution,source_url}` with nonempty strings and optional `background:"light"|"dark"`. `GET /v1/providers?specialty=pdr&postal_code=80202&mobile_only=true`. Only public opted-in providers appear; no fuzzy radius represented as exact distance. Participating logos use the original owner's fixed public shop-logo route. The same `media` shape appears on `/v1/discovery` listings. Reviewed official business logos/photos use the fixed local public-artwork route described below; Commons fallback photos require an explicit OSM File reference and verified creator/license metadata. Clients display credit/source and use a neutral image fallback; media does not establish specialty or booking eligibility.

Request: `id`, `vehicle_id`, `provider_id`, `specialty`, nullable `service_mode`, `description`, `preferred_time`, `proposed_slots`, `status`, `delivery_status`, `created_at`, `updated_at`, `scheduled_at` (nullable ISO datetime), `events` (array of {status, message, created_at}). `POST /v1/requests` accepts vehicle_id, provider_id, specialty, description, preferred_time, share_contact (must be true), optional `service_mode:null|shop_visit|mobile`, and Calendar fields `calendar_check` (default false), `duration_minutes` (default 60), `calendar_generation` (default null), `proposed_slots` (default empty; at most three distinct offset-aware ISO timestamps). Structured slots require `calendar_check=true` and current checked availability; manual timing uses `preferred_time`. The returned record also includes the frozen Calendar zone/generation and sync status fields described below. Requires `Idempotency-Key`; POST /v1/requests/{id}/cancel cancels when permitted. GET /v1/requests lists only owned requests. Live requests require a configured bridge and saved normalized five-digit service ZIP. Omitted mode retains legacy exact service-ZIP coverage. Explicit mobile mode requires declared mobile service plus that coverage; shop visits require an accepting participating shop, matching specialty and a fresh server-checked location within 30 miles of the ZIP center. Public OSM identifiers are never bridge targets. Retries with the same key/body return the original request; changing the body conflicts.

Estimate: `id`, `vehicle_id`, `discipline` (`pdr` or `collision`), `description`, `claim_number`, `date_of_loss`, `status` (`draft`, `submitted`, `reviewing`, `ready`, `approved`), `amount_cents` (nullable integer), `provider_name`, `provider_id` (nullable), `delivery_status` (`draft`, `queued`, `failed`, `delivered`), `processing_state` (`not_started`, `pending`, `processing`, `failed`, `complete`), `processing_error` (nullable safe text), `updated_at`, `photos` (array of {id, label}). `POST /v1/estimates` creates a draft, required vehicle_id/discipline/description (at most 2000 characters) and optional claim_number/date_of_loss. While an estimate is still an unshared draft (`status` and `delivery_status` both `draft`, `processing_state` `not_started`) the customer may `PUT /v1/estimates/{id}` with any of description/claim_number/date_of_loss, `DELETE /v1/estimates/{id}` (removes its photos and capture receipts, 204), and `DELETE /v1/estimates/{id}/photos/{photo_id}` (204). Once shared, those routes return 409 with `{"detail":"This estimate has been shared and can no longer be changed.","code":"estimate_locked"}`. `POST /v1/estimates/{id}/photos` multipart file + label uploads or replaces a private JPEG/PNG/WebP with size/type validation; `GET /v1/estimates/{id}/photos/{photo_id}` requires the customer's bearer token. The nine required documentation labels are `vin`, `odometer`, `engine_bay`, `interior`, `tire_tread`, `front`, `driver`, `rear`, `passenger`. PDR additionally needs a legacy `panel_<type>` photo or a complete `hail_close_<panel>` / `hail_raking_<panel>` pair for a supported area; incomplete pairs are rejected and a complete pair supersedes its legacy single photo. Use the `pdr_damage_panel_types` capability and guided-capture contract; this is evidence for the original assessor, not a quoted pricing row. Collision may include `corner_fl`, `corner_fr`, `corner_rl`, `corner_rr`, and `roof`. Photo storage is capped per customer and uploads/submits have database-backed hourly rate limits.

`POST /v1/estimates/{id}/submit` accepts `{"provider_id":"<Plus provider id>","share_contact":true}` with optional `service_mode:null|shop_visit|mobile`, plus `Idempotency-Key: estimate:<id>` (any stable nonempty key up to 200 characters is accepted). The server requires an owned draft, saved name and reachable phone of at most 40 characters with at least seven digits, saved valid ZIP, a visible opted-in accepting **shop** with matching discipline and admitted service mode/location, all required private files, and the additional PDR damage photo. Receiver-compatible vehicle fields are checked before queueing: year 1950..2050, make/model 1..60 characters, nonempty VIN exactly 17 permitted characters, mileage 0..9,999,999, and claim number at most 60 characters. The server freezes the customer-approved contact, vehicle, provider, service ZIP, and SHA-256 photo manifest in one transaction with a durable outbox row. Successful same-key/body retries return the same estimate; a changed key/body after submission returns 409. `status=submitted` means the customer submitted to Plus; `delivery_status` separately shows upstream delivery. No amount is shown until an authoritative original-Estimoto snapshot supplies it. Photo uploads are locked after submission.

Repair: `id`, `vehicle_id`, `provider_name`, `title`, `status`, `updated_at`, `estimated_completion` (nullable ISO date), `stages` (array of {title, status: completed/current/upcoming, date: nullable ISO date}). Supplied only by the authenticated bridge.

Reminder: `id`, `vehicle_id`, `title`, `due_date` (nullable YYYY-MM-DD), `due_mileage` (nullable integer), `completed` (boolean). POST /v1/reminders creates a reminder (at least one due field required); POST /v1/reminders/{id}/complete completes it; `PUT /v1/reminders/{id}` changes any field (the merged result still needs a date or mileage); `DELETE /v1/reminders/{id}` returns 204; `POST /v1/reminders/{id}/reopen` clears completion. Reminders owned by another customer return 404.

`POST /v1/assistant` accepts `message` (1..2000 chars), `vehicle_id` (nullable owned vehicle), `postal_code`, `specialty` (nullable), `mobile_only` (boolean). Returns `reply`, `intent` (including `advice`, `find_provider`, `clarify`, `shop_outreach`), `specialty` (nullable), `providers` (Provider[]), `videos` ({title, url, source}[]), and optional `answer_source: "AI guidance"` when a bounded model call succeeds. Discovery answers also return a `discovery` envelope; saved-shop/history answers can return owned references such as `dedicated_shop_id`. Source-backed replies may include `sources`. The assistant never mutates a request or invents diagnosis, appointments or availability. Only nonurgent advice for nondemo customers may call the model, capped by a persistent 30 requests per customer per hour; deterministic fallback remains useful without AI keys or on errors. Tire-pressure questions carry a labeled [Michelin USA video](https://www.youtube.com/watch?v=dn0ShsQRgho).

## Notifications

Customer-visible state changes create durable notices: a provider event on a delivered request (`request_accepted`, `request_declined`, `request_scheduled`, `request_completed`, `request_cancelled`), a trusted estimate snapshot that first carries a ready amount (`estimate_ready`) or a failed processing state (`estimate_failed`), a shop confirming an offered time (`shop_confirmed`) and a reminder whose due date has passed or whose due mileage the vehicle has reached (`reminder_due`, scanned by the worker every five minutes). Each notice has a dedupe key, so replayed events and repeated scans never create a second one. `GET /v1/notifications` returns `{"notifications":[{id, kind, title, body, source_kind, source_id, created_at, read_at}], "unread": n, "email_updates": bool}` with the newest 50. `POST /v1/notifications/read` with `{"ids":[…]}` or `{"all":true}` marks notices read and returns the new unread count. `PUT /v1/notifications/preferences` with `{"email_updates": bool}` controls email delivery.

The worker emails each pending notice once through Resend (`RESEND_API_KEY`, `EMAIL_FROM`) with idempotency key `customer-notification:<id>`, skipping demo customers and customers who turned email updates off; when email is not configured the notice stays in the app and is retried later. Transient failures back off and give up after eight attempts. Push notifications are not implemented; they need APNs/FCM credentials and a native build.

## Client error reports

`POST /v1/client-errors` (no authentication) accepts `{platform: ios|android|web|other, app_version, build_number, source_sha, kind, message, stack}` from the app's global error handlers and answers 202. Email addresses, phone numbers and bearer tokens are redacted before storage, identical errors on the same day fold into one row with an occurrence count, nothing identifying the customer is stored, and rows older than 30 days are pruned. `GET /v1/bridge/client-errors` (bridge key) lists the latest 100 for operators. The route is limited per client IP.

## Abuse guard

An IP-based guard (Fly-Client-IP, then X-Forwarded-For, then the socket address) throttles more than 60 unauthenticated 401 responses per IP per minute on `/v1/*` with 429 and `Retry-After`, so a token spray cannot amplify into the identity provider, and limits the public `/android/current`, `/android/download`, `/v1/shop-actions/*` and `/v1/client-errors` routes to 30 requests per IP per minute. Health and readiness routes are never limited. The Android release pointer is cached in-process for 60 seconds.

## Account export and deletion

`GET /v1/account/export` returns everything the customer can see, as one JSON document with `Content-Disposition: attachment; filename="estimoto-plus-export.json"`: `format` (`estimoto-plus/1`), `exported_at`, `profile`, `vehicles` (with `has_private_photo`), `reminders`, `estimates` (with photo identifiers), `requests`, `repairs`, `service_history` (`records` with receipt metadata, `preferences`, `policy_version`, `consent_events`), `my_shops`, `shop_requests`, `dedicated_shops`, `vehicle_valuations`, `notifications` (email preference and items) and `calendar` (status, selected calendar identifiers, time zone). Photo and receipt bytes are not embedded; their identifiers resolve through the existing owner-scoped routes while the account exists. Limited to 10 exports per customer per hour.

`DELETE /v1/account` permanently erases the account. Open service requests (`requested`, `accepted`, `scheduled`) are cancelled exactly as customer cancellation does; when a cancellation tombstone is owed to the shop bridge it is delivered synchronously first, and if the bridge cannot be reached the call returns 409 `{"detail":"…","code":"open_requests"}` with the requests already cancelled and no data removed, so the customer can retry. Otherwise, in one transaction, every row the customer owns is deleted: vehicles, private vehicle photos, estimates, capture receipts and photos, outbox rows, requests and events, repairs, reminders, service history, receipts, the private knowledge graph, consent events and preferences, saved shops and scheduling requests (unsent shop emails are discarded, and a sent shop's confirmation link stops working), calendar connection rows, dedicated shops, valuation history and rate counters, then the customer row. Private files are unlinked afterwards, the verified-session cache entry is invalidated, and when `SUPABASE_SERVICE_ROLE_KEY` is configured the Supabase Auth user is removed through the admin API. The response is `{"deleted":true,"sign_in_removed":<bool>,"requests_cancelled":<n>,"files_removed":<n>}`. `sign_in_removed=false` means the identity still exists upstream (no service key, or the admin call failed); signing in again then creates a fresh, empty customer. Demo sessions receive 403. Limited to 5 attempts per customer per hour.

Unbounded creation is capped per account: 50 vehicles, 500 estimates and 500 reminders. Exceeding a cap returns 409 `{"detail":"…","code":"limit_reached"}`.

## Authentication behavior

A per-app pooled client verifies Supabase identities at the fixed `/auth/v1/user` endpoint. GET/HEAD may reuse a successful verification for at most 15 seconds from verification start and never past JWT expiry. The bounded cache stores identity projections under a token hash, not raw bearer tokens, mutable metadata, errors or negative results. Writes verify fresh and invalidate cached reads. JWT claims only bound cache lifetime; they do not replace upstream authentication. An uncached upstream outage/rate limit returns 503, while invalid credentials return 401. Ownership checks still run on every private record lookup.

## Discovery and public business artwork

`GET /v1/discovery` accepts `postal_code` (or saved profile ZIP), `radius_miles=30`, optional owned `vehicle_id`, optional `specialty`, and `mobile_only`. It returns `postal_code`, `radius_miles`, `distance_basis:"zip_centroid"`, `status:"ready"|"stale"|"unavailable"`, `exhaustive:false`, `truncated`, `checked_at`, `source_attributions`, `providers`, `shop_visit_alternatives`, and `message`. A completed search adds `result_limit:30` and `selection:"reviewed_businesses"`; the two listing arrays share that cap. Early unavailable responses may omit those two selection fields. Distances are approximate straight-line distances from the ZIP center.

Participating rows retain `source:"estimoto"`, their Plus provider ID and published `source_id`; their `request_modes` determine which reviewed handoffs are offered. Public rows retain `source:"openstreetmap"`, an `osm:node:…`/way/relation listing ID and the underlying `node:…`/way/relation `source_id`, with `accepting_requests:false` and no bridge request modes. Public entries must exactly match a reviewed source name, address and map point. Business/contact reviews expire after 90 days; fresh public-cache and identity checks are separate from artwork availability.

Profiles include official `website`, `phone`, `description`, `service_details`, `phone_kind`, `specialty_evidence`, `vehicle_match`, `favorite`, and `favorite_references` where supplied. Public `verification` includes `status:"contact_confirmed"`, `checked_at`, official `source_url`, formatted `address`, and the review `scope`. This confirms published business/contact details, not workmanship, certification or appointment availability. Explicit official make listings or supported OSM make tags can produce `vehicle_match.status:"listed_make"`; shop names and chain branding cannot. No Google rating is fabricated or inferred.

Official logos/photos use `/public/shop-media/{node|way|relation}/{number}/{sha256}.png`. The catalog binds artwork to an exact listing; the route rechecks current business review, cached public listing identity and requested digest. Approved PNGs are at most 512×512 and 512 KiB, with a one-day public cache and digest ETag. This is a fixed catalog, not an arbitrary image proxy. Participating logos keep their original opt-in-controlled route; licensed Commons fallback photos retain their own credit/source. Clients honor the optional media background hint without recoloring the artwork and provide a neutral fallback.

`GET /v1/discovery/favorites?vehicle_id=...` returns private `{vehicle_id,specialty,source,source_id}` references. `PUT /v1/discovery/favorites/{specialty}` accepts `{vehicle_id,source,source_id}`; `DELETE` on the same path takes `vehicle_id`. Sources include `estimoto`, `openstreetmap`, and owned `my_shop`. Saving a favorite sends no message. See [local discovery](../backend/docs/local-discovery.md) for cache, attribution, quotas and admission details.

## Vehicle imagery and valuation

| Route | Contract |
| --- | --- |
| `GET /v1/vehicles/{id}/image` | Owner-only canonical WebP; uploaded photo first, representative CarsXE image second, or 204 with `Retry-After`. Image responses carry `X-Vehicle-Image-Source: upload|carsxe`, an ETag and private/no-store headers. |
| `POST /v1/vehicles/{id}/image` | One multipart `file`; static JPEG/PNG/WebP up to 10 MB and 40 megapixels. Stores sanitized WebP and returns `{source:"upload",image_version}`. |
| `DELETE /v1/vehicles/{id}/image` | Revokes the private upload, returns 204; subsequent reads can return representative imagery. |
| `GET /v1/vehicles/{id}/valuations` | Newest-first list of the customer's own lookups for that vehicle: `{vehicle_id, valuations:[{id, state, condition, mileage, created_at, payload:{buckets:[...]}}]}`, capped at 50 per vehicle. `DELETE /v1/vehicles/{id}/valuations/{valuation_id}` removes one (204). Only `available` results are recorded. |
| `POST /v1/vehicles/{id}/valuation` | Explicit lookup body `{state:"CO",condition:"excellent"|"clean"|"average"|"rough"}`. Uses the owned saved VIN and mileage; state must be a supported US state/DC abbreviation. |

Valuation returns `vehicle_id`, `status:"available"|"pending"|"unavailable"`, `provider:"CarsXE"`, `currency:"USD"`, selected `state`/`condition`, `mileage`, cache/fetch/expiry metadata, provider region/date, `buckets`, private `history`, safe `message`, and optional retry delay. Each retail/wholesale bucket includes `amount_cents`, `amount_basis`, `base_cents` and mileage/equipment/regional adjustment cents. Only valid matching provider figures appear. Saved history counts/costs remain separate, are never added to market value and are not sent to CarsXE. VIN/key/raw provider responses are not exposed in the valuation response. The Flutter demo returns explicitly labeled fixed fictional values locally, without a provider call; this is not a live API valuation result. See [private vehicle imagery](../backend/docs/vehicle-images.md).

## Guided capture, history and scheduling

Guided estimate routes live under `/v1/estimates/{id}/capture`: state, photo upload, VIN recognition/confirmation and capture help. They enforce owned draft writes, bounded bytes, immutable operation identity and explicit VIN confirmation against the current image hash and saved VIN. New bridge payloads use capture version 2; frozen older receipts retain their original contract. Framing assistance is not damage assessment. See [customer capture](../backend/docs/customer-capture.md).

`/v1/my-shops` supports private list/create/edit/delete contacts. `/v1/shop-outreach` supports draft creation/list/detail; `POST /v1/shop-outreach/{id}/authorize` requires the reviewed hash, contact-sharing consent and an idempotency key. Draft creation contacts nobody. Authorization either queues the exact reviewed email or returns `call_required` with a validated call link for a phone-only shop. The app opens the dialer only after the customer taps Call. The Flutter demo mirrors that call transition while keeping email delivery as a local preview. `DELETE /v1/shop-outreach/{id}` discards a request whose status is `draft`, `call_required` or `delivery_failed` (204; other statuses return 409). `POST /v1/shop-outreach/{id}/withdraw` moves a `queued`, `delivery_unknown` or `waiting_for_reply` request to `withdrawn`, finishes any undelivered outbox row, and makes the shop's confirmation link answer 410 "This request was withdrawn by the customer."; no message is sent to the shop.

`GET /v1/knowledge`, `POST /v1/knowledge/records`, `PUT /v1/knowledge/records/{id}` (any subset of the create fields except vehicle_id; receipts stay attached and the private graph is re-projected), record deletion, private graph reads and `PUT /v1/knowledge/preferences` manage customer-reported service/parts/cost history and optional aggregate-sharing consent. Receipt upload/read/delete routes under `/v1/knowledge/records/{id}/receipts` require ownership; exact bytes stay private and are never public artwork or model-training material. See [history and receipts](../backend/docs/history-receipts.md) for file limits, PDF checks and retry/tombstone behavior.

Calendar routes are under `/v1/calendar/google`: status, connect/reconcile, calendars, preferences, availability, connection deletion and sync retry. Preferences select 1–10 accessible calendars, a valid IANA `time_zone`, and explicit `sync_confirmed`. New connections have an empty unconfigured zone; the client suggests a validated device IANA zone only for that empty state and saves it only on explicit preference save. Existing choices, including UTC, survive reconnect. If device-zone resolution fails, the user must choose a valid zone. The demo uses America/Denver and performs no Google calls.

Availability requires the saved zone, a 30–480 minute duration and a window at most 14 days, within 90 days and starting more than one hour ahead. It returns at most 12 checked slots plus generation/time-zone/duration metadata. Checked requests freeze `calendar_check`, `calendar_generation`, `calendar_time_zone`, `duration_minutes` and sync state; selected IDs stay private. Only explicitly enabled checked confirmed appointments can be copied to Google. Feature configuration and verified OAuth setup are separate from implementation; see [Google Calendar](../backend/docs/google-calendar.md).

`POST /v1/dev/session` exists only under explicit development/demo configuration, returns `access_token` and `demo:true`; it seeds fictional data for a single demo identity. Release-mode customer login uses Supabase; demo sessions are never accepted in production.

Bridge routes require a separate `X-Bridge-Key` and never accept customer tokens as authority. POST /v1/bridge/providers upserts an opt-in provider including `public_visible` and source IDs; `POST /v1/bridge/sync` also pulls the original Estimoto `GET /bridge/plus/providers` catalog, including opt-out rows, hides previously listed providers absent from the complete catalog, and pulls `GET /bridge/plus/requests/{id}` events bound by request ID, provider source ID, and durable receipt. Production estimate creation requires a successful fresh provider-catalog pull before delivery. The production background worker performs these pulls. POST /v1/bridge/requests/{id}/events accepts event_id, provider_id, status, message and optional scheduled_at, with replay protection and transition checks. Trusted estimate/repair snapshot endpoints bind records to an existing explicit customer/vehicle relationship; email/VIN cannot claim records. For a locally submitted estimate, the snapshot must additionally carry `estimate_id` and matching `provider_source_id`, and can only advance status. `ready`/`approved` require an authoritative amount. `processing_state=failed` is terminal for that immutable submission and exposes the receiver's safe `processing_error`; transient bridge outages leave processing retryable.

The estimate outbox POSTs to fixed `BRIDGE_ESTIMATE_URL` (`/bridge/plus/estimates`) with `Idempotency-Key: estimate:<estimate_id>` and frozen fields `event` (`submitted`), `estimate_id`, `customer_id`, `vehicle_id`, `provider_source_id`, `service_postal_code`, `discipline`, `description`, `claim_number`, `date_of_loss`, `capture_version:2`, optional `service_mode`, `contact` (name/email/phone/contact_preference), `vehicle` (year/make/model/VIN/mileage; insurance policy omitted), and `photos` (`id`, `label`, `sha256`, `byte_size`, `mime_type`). The receiver returns a durable `{ "receipt_id": "..." }` only after saving its job/intake. It imports private bytes through fixed `GET /v1/bridge/estimates/{estimate_id}/photos/{photo_id}` with `X-Bridge-Key`; the Plus API verifies the frozen photo hash and never accepts a customer-supplied fetch URL. Later worker calls `POST /bridge/plus/estimates/{id}/process` until processing completes, then polls `GET /bridge/plus/estimates/{id}` for authoritative status. Each response must include explicit local estimate/customer/vehicle/provider binding and `source_id`, `status`, nullable `amount_cents`, `processing_state`, nullable `processing_error`, and `updated_at`. The original assessor decides whether PDR evidence supports a real quote; Plus never invents a figure or approval.

Service-request durable outbox delivery POSTs to fixed `BRIDGE_REQUEST_URL` with `Idempotency-Key`; only a persisted upstream receipt counts as delivered. The creation payload freezes approved contact/vehicle fields and service ZIP. A cancellation tombstone may arrive before delayed creation: the receiver must persist it and neutralize any late creation before acknowledging. Both outboxes use database claim leases and retries. Production settings require dedicated PostgreSQL, Supabase Auth URL/publishable key, both fixed HTTPS bridge URLs, bridge key, mounted private photo volume, and `SOURCE_SHA`; `WORKER_ENABLED` defaults true in production and `WORKER_INTERVAL_SECONDS` defaults 15 (allowed 5–300). Optional `WEB_DIR` mounts the built Flutter web app at `/` after API routes. `GET /health/live`, `GET /ready` (database/migration/photo volume), and `GET /version` (`source_sha`) expose deployment state without secrets. The migration chain enables row-level security and revokes Supabase Data API table access from `anon`/`authenticated`; the app connects as the private table-owning database role.
